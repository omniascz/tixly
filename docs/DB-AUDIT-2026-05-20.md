## 4. P1: 112/119 tabulek s `promoter_id` BEZ RLS ❌

**Stav RLS-enabled tables:** 18 z 407. Z toho:
- `platform.promoters`, `orders.orders`, `tickets.tickets` — ✅ OK
- `platform.fee_schedules`, `platform.payouts`, `platform.payout_events` — ✅ OK
- `loyalty.accounts`, `loyalty.transactions` — ✅
- `verified_fan.registrations` — ✅
- `payments.wero_payments`, `payments.wero_webhooks` — ✅
- ... 7 dalších

**Tabulky které by měly mít RLS ale nemají:**
- `catalog.events` — promotér by neměl vidět cizí akce v admin queries
- `catalog.venues` — multi-tenant venues
- `catalog.ticket_types` — pricing privacy
- `catalog.access_codes` — privacy
- `marketing.*` — všech 8 tabulek (campaigns, affiliates, vouchers, atd.)
- `orders.invoices` — finanční data
- `orders.refund_requests` — privacy
- `audit.platform_log` — cross-tenant log leak risk

**Důsledek:** Bug v WHERE klauzuli → leak dat napříč promotéry.
DB-level guard chybí.

**Fix:** Migration 282 — ENABLE RLS + policy `USING (promoter_id =
current_setting('app.current_promoter_id')::uuid)` na klíčové tabulky.
**Vyžaduje:** app.current_promoter_id = SET LOCAL při každém request (middleware).

## 5. P1: `identity.users` PII split na first_name/last_name ❌

**Stav současný:** `identity.users.name` = single text column.

**Pattern v CZ trhu:**
- Faktury vyžadují jméno + příjmení jako 2 pole (ISDOC, daňové doklady)
- ČNB AML/KYC formuláře
- Volání zákazníka jménem ("Dobrý den, pane Nováku")
- Sorting podle příjmení v admin

**Tabulky s problémem:**
- `identity.users.name` ← KRITICKÉ
- `tickets.tickets.holder_name`
- `orders.invoices.customer_name`
- `marketing.newsletter_subscribers.name`
- `subscriptions.holders.holder_name`

**Tabulky které už mají správně:**
- `platform.staff_members` (first_name + last_name)
- `conference.exhibitor_staff.full_name` (jiný style, OK pro tento context)
- `conference.speakers.full_name`

**Fix:** Migration 283 — ADD COLUMN first_name + last_name (nullable),
backfill heuristikou (`SPLIT_PART(name, ' ', 1)` + `SUBSTRING(name FROM POSITION(' ' IN name) + 1)`),
pak app může `COALESCE(first_name || ' ' || last_name, name)`.

**Edge cases:**
- "Jan Novák" → "Jan" / "Novák"
- "Jana Marie Novák" → "Jana Marie" / "Novák" (jeden mezerník nestačí, ale 80% real cases)
- "Ing. Jan Novák, Ph.D." → fallback na `name` jako celek (manual review)
- Single-word users (cizinci) → first_name = full, last_name = NULL

## 6. ~~P2: 274/280 venues = orphan~~ → ✅ FALSE POSITIVE

**Re-investigation:** Původní LEFT JOIN query čítal venues s `promoter_id IS NULL`
jako "orphans". Po re-check:
- 274 venues mají `promoter_id = NULL` (= master-admin venues, sdílené)
- 0 venues má broken FK ref

**Architektura (podle memory `project_seat_mapping_architecture`):**
Master admin maluje fyziku sálu (O2 Arena, Letná, Rudolfinum), promotéři
si dělají vlastní seat mapping per akce. Master venues nepatří žádnému
promotérovi — `promoter_id = NULL` je správný design.

**Akce:** Žádná. Migrace 281 byla aplikována (DELETE 0 rows) — bezpečně.

## 7. P2: 30 tabulek s `promoter_id` BEZ indexu ❌

**Důsledek:** Multi-tenant query `WHERE promoter_id = $1` dělá full table scan.
Při velkém volumu (10k+ promotérů × 100k+ rows) = pomalé.

**Příklady:**
- `accreditation.accreditation_requests`
- `audit.platform_log` — vysoký volume!
- `catalog.access_codes`
- `catalog.payment_plans`
- `marketing.affiliates`
- `orders.bank_transfer_imports`
- `risk.fraud_cases`
- `segmentation.export_jobs`
- `sport.season_ticket_holders`
- `surveys.surveys`
- ... 20 dalších

**Fix:** Migration 284 — `CREATE INDEX CONCURRENTLY idx_<tab>_promoter ON <tab>(promoter_id);`
