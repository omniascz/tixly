## P0 — Must fix before production

### BUG-001: GoPay webhook never marks orders as paid — gopay-payments
**Severity:** P0
**Type:** Broken integration / lost revenue
**Location:** `gopay-payments/src/services/gopay-payment.service.ts:248-277` (handleGopayWebhook) + missing consumer anywhere in repo
**Description:** The webhook handler updates only `payments.gopay_payments` and emits a Kafka event `gopay.payment.paid`. Grep for that topic across all `src/**/*.ts` yields only the producer + its test. No consumer exists anywhere (checked entire monorepo). Orders in `orders.orders` therefore never transition to `paid` state after a GoPay payment.
**Reproduction:** Pay any order via GoPay → webhook fires → `gopay_payments.status = 'PAID'` but the order still shows `status = 'pending'`. Buyer never receives ticket.
**Fix:** Either add a Kafka consumer that updates `orders.orders` on `gopay.payment.paid`, or have `handleGopayWebhook` mark the order paid directly inside the existing transaction (analogous to `bank-reconciliation.markOrderPaid`).

### BUG-002: ems-booking ↔ permanentky integration is completely missing
**Severity:** P0
**Type:** Broken integration / fitness revenue model unusable
**Location:** `ems-booking/src/**` (no permanentky references), `permanentky/src/**` (no ems references)
**Description:** The spec requires that when an EMS reservation is confirmed, a credit is consumed from the client's permanentka; on cancel/refund, a credit is refunded. Neither side contains any import, Kafka consumer, or HTTP call to the other. `permanentky.consumeCredit` is only invoked from its own tests. `ems-booking` has no import of `permanentky` at all.
**Reproduction:** Book EMS lesson as a permanentka holder → `remaining_credits` stays unchanged → customer gets unlimited free lessons.
**Fix:** Add a reservation-confirmed consumer (either Kafka subscriber in permanentky, or a direct service call in `ems-reservation.service.ts`) that calls `consumeCredit({ packageId, clientId, reservationId })`, plus a refund handler for cancellations.

### BUG-003: referral-system has no database schema and no tests
**Severity:** P0
**Type:** Missing migration / runtime crash
**Location:** `referral-system/src/services/*.ts` (8 files query `FROM referral.*` tables); `migrations/` (no `referral.*` CREATE TABLE anywhere)
**Description:** All services in `referral-system` query the `referral.*` schema (conversions, credit, clicks, links, leaderboard), but there are no migrations creating that schema. Module has zero tests. First production query will throw `relation "referral.*" does not exist`.
**Fix:** Add migration creating `referral.referral_links`, `referral.clicks`, `referral.conversions`, `referral.credits`, `referral.leaderboard`. Add at least smoke tests.

### BUG-004: Generic rollback handler allows SQL injection via stored action log — action-log
**Severity:** P0
**Type:** SQL injection
**Location:** `action-log/src/lib/default-handlers.ts:44-81` (`genericJsonRollbackHandler`)
**Description:** The handler builds `UPDATE ${table} SET ${col} = $1, ...` by interpolating `table` and column names directly from `action.beforeState`, which is a JSONB column persisted per audit entry. Any code path that writes a crafted `beforeState` (or a compromised admin editing audit rows) gets arbitrary SQL execution against any table. The code comment explicitly acknowledges: *"Bezpečnostní filtr: table musí být whitelist-controlled callerem"* — but no whitelist is enforced in the default handler itself.
**Fix:** Whitelist allowed tables and validate column names against `^[a-z_][a-z0-9_]*$` inside the handler, not just at callsite. Quote identifiers or reject unknown ones.

### BUG-005: landing-pages block renderer — stored XSS
**Severity:** P0
**Type:** XSS (two vectors)
**Location:** `landing-pages/src/lib/block-renderer.ts`
**Description:** Two XSS holes:
1. Line 42-44: `text` block's `data.html` is written to the page **raw** with comment *"data.html is trusted content from CMS — passthrough"*. CMS content is authored by promoters, not developers — promoters are untrusted tenants in a SaaS platform. A malicious promoter can embed `<script>` to attack visitors.
2. Lines 36, 48, 55: URL attributes (`ctaUrl`, `img.src`, `url`) use `escapeHtml()` only. `escapeHtml("javascript:alert(1)")` returns `javascript:alert(1)` unchanged — HTML entity escaping does not neutralize URL schemes. Click the CTA and JS executes in the visitor's context.
**Fix:** Use DOMPurify (or similar) for HTML blocks. Validate URLs against allowlist schemes (`http:`, `https:`, `mailto:`, `tel:`) and reject `javascript:`, `data:`, `vbscript:`.

## P1 — Should fix soon

### BUG-006: Bank reconciliation multi-step writes not transactional
**Severity:** P1
**Type:** Data consistency
**Location:** `bank-reconciliation/src/services/reconciliation.service.ts:171-174` (`pollAndReconcile` loop)
**Description:** `updatePaymentStatus` (UPDATE bank_payments) and `markOrderPaid` (UPDATE orders + Kafka emit) are called sequentially without a wrapping transaction. A crash or DB error between them leaves `bank_payments` marked `matched` while `orders` stays `pending`, or the other way around. Kafka emit inside `markOrderPaid` is also outside any tx — produces inconsistency between DB and message log.
**Fix:** Wrap both UPDATEs in `deps.db.transaction(async tx => { ... })`; emit Kafka event after commit with the transactional outbox pattern (or accept at-most-once for now, but at least make DB consistent).

### BUG-007: fitness-reminders silently swallows SMS failure when env var missing
**Severity:** P1
**Type:** Silent failure
**Location:** `fitness-reminders/src/services/reminder.service.ts:278-289`
**Description:**
```ts
const base = process.env.INTERNAL_API_BASE_URL ?? '';
if (base) { await fetch(`${base}/api/sms/send`, ...) }
return { status: 'sent' };
```
If `INTERNAL_API_BASE_URL` is unset (or empty string in misconfigured env), the fetch is skipped and the reminder is reported as `sent`. Rows in `reminders` table will be marked sent without SMS being delivered. Also: no auth header on the internal API call — anyone who reaches the `/api/sms/send` endpoint can spam SMS.
**Fix:** Throw/fail the reminder if `base` is not configured. Add a shared-secret header (`X-Internal-Token`) checked by the `bulkgate-sms` route.

### BUG-008: referral-system treats money as floats and parseFloats it
**Severity:** P1
**Type:** Float money arithmetic / precision loss
**Location:**
- `referral-system/src/services/credit.service.ts:50` — `amountCzk: parseFloat(row.amount_czk)`
- `referral-system/src/services/conversion.service.ts:50` — `orderAmountCzk: parseFloat(row.order_amount_czk)`
- `referral-system/src/lib/attribution.ts:98` — `Math.round((x + remainder) * 100) / 100`
- `referral-system/src/jobs/referral-scheduler.job.ts:95` — `parseFloat(row.amount_czk)`
**Description:** The rest of the monorepo uses `*_halire INTEGER` (`gopay-payments`, `bank-reconciliation`, `payout-management`, `permanentky`, etc.), but `referral-system` stores and computes money as CZK float (NUMERIC cast via parseFloat). Multi-way splits via `Math.round((share + remainder) * 100) / 100` accumulate rounding error.
**Fix:** Migrate columns to `*_halire INTEGER` or `NUMERIC(14,0)` halíře. Use integer arithmetic for splits.

### BUG-009: fitness-portal uses deep relative cross-module import and duplicates rules
**Severity:** P1
**Type:** Fragile cross-module coupling / rule drift
**Location:**
- `fitness-portal/src/app/api/fitness-portal/me/reservations/[reservationId]/cancel/route.ts:9`
- `.../reschedule/route.ts:9-13`
- `fitness-portal/src/services/fitness-portal.service.ts:22` — comment "inline duplikát ems-booking pravidel"
**Description:** Route files import `../../../../../../../../../ems-booking/src/services/ems-reservation.service.js` (9 levels up, direct path, not a package). Any rename of ems-booking directory breaks fitness-portal silently at build. Additionally, cancellation rules are copy-pasted between the two modules — they will drift.
**Fix:** Make `ems-booking` a proper workspace package and import by name. Delete the duplicated rules in `fitness-portal.service.ts`.

### BUG-010: buyer-portal PDF route dynamic import likely broken
**Severity:** P1
**Type:** Broken integration
**Location:** `buyer-portal/src/app/api/portal/me/tickets/[ticketId]/pdf/route.ts:27`
**Description:** `await import('pdf-ticket' as any).catch(() => null)`. `'pdf-ticket'` is neither a published npm package nor a relative path — this import will always reject and `pdfMod` will always be `null`, causing the fallback path to run. Silenced by the empty `.catch(() => null)` so there's no error in logs.
**Fix:** Use a relative path (e.g. `'../../../../../../../../../pdf-ticket/src/index.js'`) or make it a workspace package. Also remove the catch so genuine import errors surface.

### BUG-011: Several admin/system UPDATEs without tenant scoping
**Severity:** P1
**Type:** Cross-tenant leak potential
**Location:**
- `buyer-blacklist/src/services/blacklist.service.ts:213,360,421` — `WHERE id = $1`
- `bulk-email/src/services/bulk-email.service.ts:152,219` — update by id with no promoter scope
- `branch-management/src/services/branch.service.ts:255,323` — delete branch by id, promoter_id only checked in one of two paths
- `ambassador-management/src/services/ambassador.service.ts:95,205,358` — id-only updates
**Description:** These queries trust that the caller already verified tenant ownership at the service boundary — but several callsites I sampled do NOT do that explicit check first. Any broken auth/permission check anywhere in the chain lets promoter A mutate promoter B's rows. Defense-in-depth missing.
**Fix:** Add `AND promoter_id = $N` to all mutating queries in tenant-scoped tables, even if the caller also checks.

## Audit notes

**What was scanned.** Phase-1 glob of top-level modules; grep sweeps for SQL interpolation, money floats, tenant scoping, empty catch blocks, hardcoded secrets, raw HTML output; targeted reads on `action-log/default-handlers.ts`, `landing-pages/block-renderer.ts`, `gopay-payments/webhook/route.ts`, `gopay-payments/gopay-payment.service.ts`, `bank-reconciliation/reconciliation.service.ts`, `permanentky/permanentky.service.ts`, `fitness-reminders/reminder.service.ts`. Integration wiring verified by grep for producer topic names, HTTP paths, cross-module imports.

**What was skipped (scope):**
- Authentication/authorization middleware behaviour under race conditions
- RLS policy correctness vs. service layer tenant filters
- Pricing-engine / dynamic-pricing math correctness
- Deep test quality review (presence counted, not adequacy)
- Frontend code (scanner-pwa, mobile-*, nextjs-boilerplate, micro-organizer)
- Full audit of all ~150 modules; only the 23 PulseUp-scope modules + 5 critical integration partners were looked at
- pulseup-migration column-by-column comparison against target schemas (only sampled permanentky)
- Zod validation coverage on every route (sampled only — most routes looked fine)

**Hardcoded secrets:** Grep found no obvious hardcoded API keys or passwords in scoped modules. Config loaders in gopay-payments, bank-reconciliation, bulkgate-sms all follow the `isConfigured: boolean` pattern correctly (verified bulkgate-config.ts, same pattern confirmed in others).

**Race conditions on inventory:** `permanentky.consumeCredit` correctly uses `SELECT ... FOR UPDATE` inside a transaction (verified at permanentky.service.ts:186-248). Other capacity-bearing services were not sampled — recommend a follow-up audit on `merchandise`, `flash-sales`, `ems-booking` slot capacity specifically.

**Next recommended actions:**
1. Fix the 5 P0 bugs before any production rollout (especially BUG-001 and BUG-002 which block the PulseUp launch end-to-end flow).
2. Add missing `referral-system` migration and smoke tests (BUG-003).
3. Run staging dry-run of pulseup-migration with full column validation.
4. Schedule a follow-up audit focused on race conditions in `merchandise` / `flash-sales` / `ems-booking` capacity tracking.
